# 入境用列印頁 — 設計

日期：2026-08-13

## 問題

入境日本時，入國審查官可能要求說明停留期間的住宿與行程；入境卡（外国人入国記録）也要填「日本の連絡先」的住所與電話。

現有的行程頁不適合直接拿給對方看：

- 全中文，審查官看不懂
- 一天一張卡片、15 張，還混了雨天備案、訂票網址、記帳，對方要的資訊埋在裡面
- **住宿只有飯店名稱與 Google Maps 連結，沒有地址也沒有電話** —— 正好是最需要的兩項

## 目標

產出一張 A4 可列印的雙語（英／日）摘要，只含入境情境會被問到的內容：進出境航班、每段住宿的名稱、地址、電話。

## 使用情境

出發前開啟頁面 → 列印成紙本或存成 PDF → 隨身攜帶。現場不需要網路。

## 核心決策

### 獨立檔案 `customs.html`，不塞進 `index.html`

`index.html` 已 1274 行、80KB，再加一套只為列印存在的版面與樣式，兩邊的樣式還得互相閃避。獨立頁面有自己的用途、版面與測試，邊界乾淨。

代價是 Firebase 初始化那十來行會與 `index.html` 重複。`config.js` 兩邊共用，重複的只有 `initializeApp` 與匿名登入，可接受。

### 不重新引入 `index.html` 的多語系機制

2026-08-05 的「移除多語系殘留」（`2026-08-05-remove-i18n-design.md`）刻意刪掉了 `{zh,en,ja}` 結構與 `LANG` 切換，理由是介面上沒有語言切換器、英日字串永遠不會顯示。那個判斷仍然成立。

本次的英日文只存在於 `customs.html`，寫成該檔自己的固定字串，**不動 `index.html`、不動 `t()`、不恢復 `LANG`**。行程頁維持純中文。

### 雙語並列，不做語言切換

欄位標籤寫成 `ACCOMMODATION / 宿泊先` 的形式，飯店名英日並列。地址與電話一律日文 —— 翻成英文對日方沒有意義，對方要的是能照著找到、打得通的日文住所。

一張紙通用，不必事先猜對方看哪種語言。

### 內容只留航班與住宿

不列每日行程。入境情境要確認的是「何時離境」與「住在哪裡」，逐日觀光行程反而稀釋重點，也塞不進一頁。

## 版面

A4 直式，目標一頁。

```
ITINERARY / 旅程表
2026/10/21 – 11/04  ·  15 days / 15日間

FLIGHT / 航空便
  ARRIVAL    CX530   10/21  15:30   NGO (Chubu Centrair)
  DEPARTURE  CX531   11/04  16:40   NGO (Chubu Centrair)

ACCOMMODATION / 宿泊先
  10/21 – 10/22    2 nights / 2泊
    Nagoya Garden Palace Hotel ／ 名古屋ガーデンパレス
    〒… 愛知県名古屋市…            ← 實際地址待查證核對
    TEL …                          ← 實際電話待查證核對
  （以下依連續住宿分組，共 5 段）
```

列印樣式：`@media print` 設 A4、去除背景色與陰影、隱藏列印按鈕與錯誤提示區。

## 資料來源

| 資料 | 來源 |
|---|---|
| 每日日期與住宿名稱 | Firebase `trips/<tripId>/itinerary`，與行程頁同一份 |
| 住宿地址、電話 | `customs.html` 的 `STAY_INFO` 常數 |
| 飯店英文名、日文名 | 同上（英日名可從 git 歷史取回，見下） |
| 進出境航班 | `customs.html` 的 `FLIGHTS` 常數 |

行程資料走 Firebase，所以在 app 改住宿、改日期，這頁會跟著變。地址電話與航班寫死 —— 飯店已訂、機票已開，不會變動，而放進試算表要動到 `SHEET_COLS`、`diffSheet`、編輯表單三處，代價與收益不成比例。

### 地址與電話的取得

實作的第一步，且**必須經使用者核對後才寫進檔案**。

來源是行程資料裡每天的 `stayUrl`（Google Maps 短連結）—— 使用者已確認那些連結指向的就是實際入住的那一間，所以不會拉到同連鎖的其他分店。流程：短連結解出店名與座標 → 查該飯店官網取正式地址與電話 → 用座標交叉驗證 → 列表給使用者核對。

## 住宿分組

掃過 `itinerary`，把連續相同 `stay` 的日子合併成一段，記錄起訖日期與晚數。晚數 = 該段的天數（最後一天仍住在該飯店）。

**11/04「溫暖的家」要排除** —— 那是回程日，不是在日住宿。

排除方式必須是明示的，不能靠「在 `STAY_INFO` 找不到就跳過」—— 那條路徑要留給「換了飯店但還沒登記地址」的情況，兩者混在一起會讓真正該提醒的漏登記被靜默吃掉。因此「溫暖的家」在 `STAY_INFO` 中明確登録並標記 `skip:true`，渲染時跳過。

於是規則收斂成三條，彼此互斥：

| `STAY_INFO` 狀態 | 行為 |
|---|---|
| 有登録、未標 `skip` | 正常列出名稱、地址、電話 |
| 有登録、標 `skip:true` | 不列入宿泊先（非在日住宿） |
| 沒有登録 | 列出該段與飯店名，地址電話顯示未登録 |

## 錯誤處理

| 狀況 | 行為 |
|---|---|
| 飯店名在 `STAY_INFO` 找不到（例如之後換飯店） | 仍列出該段與飯店名，地址與電話欄顯示「未登録 / not registered」（與 `skip:true` 是不同路徑，見上節） |
| Firebase 讀取失敗或回空 | 顯示明確錯誤訊息，**不印出空白表格** |

第一條的重點是不讓那一段消失。少一段住宿的紙本，比看起來完整、實際漏掉四晚要好被發現。

## 改動清單

- 新增 `customs.html`
- 新增 `tests/test-customs.js`
- `index.html`、`config.js`、既有測試皆不動

## 測試

`tests/test-customs.js` 沿用 `test-render.js` 的 DOM stub 手法（從原始碼抽出 `<script>` 區塊在 Node 裡跑），驗證：

- 分組正確：15 天的行程分成 5 段，晚數為 2 / 2 / 4 / 3 / 3
- 11/04「溫暖的家」不出現在宿泊先
- 每段都印出地址與電話
- 飯店名對不上 `STAY_INFO` 時，該段仍在，地址顯示未登録
- Firebase 回空陣列時顯示錯誤訊息，且不產生任何住宿列
- 航班兩行都印出

## 不做

- 不改 `index.html` 的任何行為，行程頁維持原樣
- 不恢復多語系機制
- 不列每日行程、不列交通估算與訂票待辦
- 不放旅客姓名（使用者決定：對方手上就有護照，紙本不必印個資）
- 不做語言切換器
